## Implementation

| File/boundary | Responsibility |
| --- | --- |
| `media.js` | Separate session/ownership, queue, XHR multipart, measured progress, accepted descriptor validation, retry/removal/status and immutable manifest controller. |
| `media-view.js` | Step 5 local object-URL previews, accessible controls/progress/errors, controlled availability changes, count/codecs, focus and teardown. |

The controller holds creation nonce, session identity and bearer in private volatile fields. None enters canonical JSON, URL, DOM dataset, browser storage or application logging. The nonce is 32 CSPRNG bytes and remains identical after uncertain session-create retries. Only a valid selection starts session creation; boot, earlier steps and zero-media submit do not call any media API.

Limits stay **5 files / 5,242,880 bytes each**. Apparent MIME/extension/size checks are UX only; the backend remains authoritative. Initial copy names JPEG/PNG/static WebP conditionally; actual session codecs update the picker/label and gate queued uploads. HEIC/HEIF is not promised. A response advertising a reduced 2 MiB contract is rejected rather than adapting to hosting.

Each selected file receives one stable `client_upload_id`. Uploads run sequentially; retry uses that same ID, file, session and bearer. XHR multipart contains only `file` and `client_upload_id`, with the ratified media marker and capability headers; the browser supplies the multipart boundary. Progress derives exclusively from upload events; unknown totals remain indeterminate. `withCredentials=false` does not itself omit same-origin browser cookies; ownership remains exclusively the bearer, never cookies/admin state. JSON media requests and report submit use `credentials:omit`.

Local preview exists before server acceptance and never uses a server original URL. Object URLs are revoked on confirmed removal, successful wizard teardown/new compilation or page exit. Back/forward navigation and other-step edits keep the same files, previews, session and submission UUID without automatically uploading again. BFCache-preserved pages retain their live memory until actual teardown.

UI lifecycle: `selected -> uploading -> accepted` or `failed`, and controlled `removing -> removed`. Duplicate content has one canonical media descriptor; visible aliases share deletion and preview cleanup. Canonical manifest order follows selection order and deduplicates by server UUID.

## Removal and uncertainty

Accepted removal waits for matching server `removed` confirmation before dropping descriptors or revoking previews. Failed removal retains the last accepted descriptor, preview and a visible error; final submit stays blocked until resolved. Never-uploaded or definitely rejected binary files can be explicitly removed locally because they have no accepted descriptor.

If an upload response is lost or its descriptor malformed, server acceptance is unknown. Removal first replays the same file/client key to recover its canonical descriptor, then calls DELETE. Failure retains the file. A later 413/validation rejection cannot erase earlier acceptance uncertainty. If replay resolves to an already-visible deduplicated image, all aliases are removed coherently after one server deletion.

Changing availability to `no`, `possible` or `surveillance` while any file remains is refused with an explicit removal prompt. After confirmed removal of the last file, availability becomes `no`; a later selection can use `yes` again. No stale descriptor enters incompatible availability variants. Zero-media payloads retain F1.6's absent `media.items` shape.

## Final submit and recovery UX

Selected/uploading/failed/removing files, and failed removals, block final submit. Error-summary links navigate to Step 5 and focus the correct file; retry/remove are real buttons, progress is associated with the filename, and live announcements exclude verbose percentage updates. Removal returns keyboard focus to a usable control.

On the first valid media-bearing final submit, the full canonical payload and ordered descriptor manifest are deeply frozen with the original submission UUID. The bearer is supplied separately in the capability header. Report remains `application/json` and `X-BadAround-Intake: badaround-report/v1`; no media marker is added to `/reports`.

Media repair is based on an explicit code allowlist (`media_reference_invalid`, `media_descriptor_mismatch`, `media_manifest_invalid`), or the existing frozen canonical correctable codes, and additionally requires owner-scoped session status `open`. HTTP 422 alone cannot authorize editing. Existing non-media field errors retain their original step/focus. The double-submit guard remains active through this asynchronous status reconciliation.

After any uncertain/retryable final response, the snapshot remains locked, even if a later response names a normally correctable media error. Pinned/binding/committed status, conflict, expiry, unknown codes or failed status checks cannot unlock it. Completed duplicate replies display normal success. No new submission/session/file identity is generated on retry.

Expiry does not introduce Save & Resume or renew deadlines. The unique session-per-submission contract is preserved: no session rotation within the current wizard. Error copy explains that a fresh submission is required for a genuinely new attempt; it never silently resets a pending intent.
