## Findings and remediation

Five initial adversarial tests failed against the initial candidate and pass after remediation:

| Finding | Consequence / correction |
| --- | --- |
| Descriptor disappeared while DELETE was unresolved | Keep the last canonical descriptor through `removing`; block final submit until confirmed removal. Failed removal preserves it. |
| Same server UUID with inconsistent descriptors silently deduplicated | Compare all four descriptor fields against an existing UUID; fail the new selection with `media_descriptor_mismatch`. Valid identical aliases still deduplicate. |
| Lost upload response replay could issue DELETE after teardown | Recheck disposal after async operations, suppress late progress/state writes, abort media requests and prohibit subsequent DELETE/queue work. |
| Wizard listeners/report completion survived teardown | Remove registered handlers, suppress late report/status completion, preserve the abandoned snapshot without fabricating success or rollback. Boot is idempotent and retains the existing logical wizard. |
| Failed selections appeared as Step 7 image previews | Preview only accepted items in final review; explicitly identify unresolved items as requiring Step 5 completion/removal. Final guard continues to block them. |

Additional adversarial inspection found that a JSON `null` XHR response could throw from the load handler and leave the upload promise unresolved. Invalid primitive/array/envelope responses now settle with `invalid_response`; completion/progress callbacks cannot act after transport cancellation/settlement. Hidden/queued Continue actions cannot advance beyond the seven-step bounds or mutate a frozen wizard.

Transport abort is best effort: it does not assert that the server undoes accepted bytes. An interrupted media upload can remain a backend orphan governed by the approved TTL/cleanup contract. A report already sent may finish server-side after teardown; the detached wizard does not mutate its snapshot or claim completion. No new submission/session is generated by teardown or retry. Ordinary back/forward navigation deliberately **retains the active upload queue**; actual page exit cancels media transport, while BFCache-preserved pages retain volatile state.

## Contract / state review

- Entire backend is byte-identical to reviewed `beb33ec…`; F1.2/F1.3 and approved F1.4/F1.5 semantics, capability model, descriptors, receipts, publication fence and schema are unchanged.
- Frozen `model.js`, shell, page/QA gate, legacy report JS/CSS and mapping architecture are unchanged. Original Step 1–4/6 field behavior, progressive disclosure, stale-value exclusion, UUID lifecycle and zero-media final submit/retry remain intact.
- Session starts only after a valid actual selection. Count/size/type rejection allocates no session. A concurrent selection shares the same creation attempt; lost create replies retry the same 32-byte CSPRNG nonce and submission identity without rotating the logical session.
- Each file gets one client UUID, stable across retry and render/navigation. Removing then selecting a different file gets a fresh UUID. Uploads are serialized; a second request cannot overtake an unresolved first request. A failed first file retried after later successes still occupies its original manifest position.
- Accepted descriptors use only server `media_id`, `mime_type`, `file_size`, `extension`. They must pass exact shape/type/UUID/codec/size/state checks. Browser MIME/extension/size prechecks are UX checks; backend is authoritative. Duplicate UUIDs require identical descriptors.
- Canonical order follows selection order across batches, delayed retry and middle-item removal, deduplicating only within the session. Maximum remains five selected files and 5,242,880 bytes per file. Exact limit accepted by UX; +1/zero/unsupported rejected. JPEG/PNG/static WebP are conditional on actual session codecs; HEIC/HEIF unsupported.
- Preview uses local object URLs only. Retry/rerender do not allocate new previews; confirmed removal, success and teardown revoke them. Late DELETE cannot double-revoke them. No original URL is requested or exposed.
- Progress is measured or indeterminate. 100 percent bytes sent remains `uploading`, with zero accepted descriptors until a valid success reply. Progress is associated with the file and excludes verbose live percentage announcements.
- Selected/uploading/failed/removing items and failed DELETEs block final submit. No silent omission. Availability cannot become `no`, `possible` or `surveillance` while an active selection remains; confirmed explicit removal is required first.
- Capability/nonce/session live in private volatile JS fields. No bearer in canonical JSON, fields, DOM attributes, local/session storage, URL, raw error dump or intentional console logging. Report uses only the dedicated header, `application/json` and the frozen intake marker; no media marker on report POST. JSON requests omit credentials; same-origin XHR cookies are not an ownership mechanism.
- First valid media submit freezes the entire payload, original UUID and ordered manifest; private capability remains the same retry context. File additions/removals/navigation cannot change the snapshot. Double submit remains blocked through async owner-status reconciliation.
- Editable errors use an exact allowlist (`media_reference_invalid`, `media_descriptor_mismatch`, `media_manifest_invalid`) or existing frozen canonical validation codes, plus owner status `open` and no previous uncertainty. Generic 4xx/retryable classification never unlocks media edits.
- Manifest conflict, incomplete upload, commit in progress, binding/invariant failure, expiry, service/rate failure, failed owner status and uncertain report response preserve the snapshot. Completed duplicate response is normal success without reupload or new session. Expiry does not silently recreate a session or invent Save & Resume.
